1. Stack y Ambiente Tecnológico

La arquitectura tecnológica de Merkostore fue concebida estratégicamente para ofrecer alta concurrencia transaccional, tolerancia a fallos, bajo consumo de recursos y una experiencia de usuario instantánea y reactiva.

1.1. Lenguajes de Programación Empleados

  • Backend: Java 21 (LTS). Aprovecha características del lenguaje como Records inmutables, Pattern Matching para switches, gestión eficiente de memoria y total compatibilidad con hilos virtuales de Project Loom.
  • Frontend: JavaScript Moderno ECMAScript 6+ (ES2023). Paradigma asíncrono con async/await, Fetch API con interceptores de autorización, Web Storage API y manipulación reactiva del DOM sin frameworks pesados.

1.2. Frameworks y Bibliotecas Backend

Framework / Biblioteca Versión Propósito y Responsabilidad en el Proyecto
Spring Boot 3.2.4 Núcleo de la aplicación empresarial; configuración no invasiva, inyección de dependencias y servidor Tomcat embebido.
Spring Security 6.2.3 Seguridad perimetral, control de accesos RBAC y arquitectura de autenticación sin estado (Stateless).
JJWT (io.jsonwebtoken) 0.12.5 Generación, firma criptográfica HMAC-SHA256 (`HS256`) y validación de JSON Web Tokens.

Jakarta Validation API 3.0.2 Validación declarativa de datos de entrada (`@Valid`, `@NotBlank`, `@Min`, `@NotNull`).
Spring Boot Actuator 3.2.4 Métricas de telemetría y salud de la aplicación en tiempo real (`/actuator/health`).

1.3. Sistema Gestor de Bases de Datos

MongoDB 7.0 (NoSQL Orientado a Documentos): Elegido debido a la naturaleza heterogénea del catálogo comercial (artículos simples al detal con unidad de medida versus combos de mercado compuestos por sub-productos anidados). La persistencia en formato BSON ofrece lectura optimizada con índices únicos sobre el código de barras/SKU y la numeración consecutiva de órdenes (`orderNumber`).

1.4. Servicios Externos e Inteligencia Artificial

  • Groq Cloud API (LPU Inference Engine): Infraestructura de aceleración de hardware para modelos de lenguaje a más de 450 tokens por segundo.
  • Meta Llama 3.1 8B Instant (`llama-3.1-8b-instant`): LLM de última generación empleado como motor conversacional RAG para asesoría de compras y armado de pedidos.
  • WhatsApp Web / App Protocol: Pasarela de comunicación mediante URL scheme (`https://wa.me/`) con codificación URI de la comanda de pedido hacia el tendero.

2. Arquitectura de la Aplicación

2.1. Descripción de la Arquitectura por Capas

El backend adopta una Arquitectura en Capas Limpia (Clean Layered Architecture), garantizando una rigurosa separación de responsabilidades y bajo acoplamiento:

Capa 1: Presentación (Frontend SPA — index.html, styles.css, app.js)
Interfaz reactiva de alta velocidad. Gestiona el estado de compras (`state`), el almacenamiento local de respaldo (`Storage`) y la navegación fluida sin recargas completas.
Capa 2: Seguridad y Filtros (SecurityConfig, JwtAuthenticationFilter)
Intercepta cada solicitud HTTP. Valida cabeceras `Authorization: Bearer `, autentica la identidad y otorga privilegios según los roles `ROLE_ADMIN` o acceso público.
Capa 3: Controladores REST (Controllers & DTOs)
Expone los endpoints HTTP. Valida la semántica de las solicitudes mediante Bean Validation y serializa las respuestas en el envoltorio uniforme `ApiResponse`.
Capa 4: Servicios del Dominio (OrderService, ChatbotService)
Aloja la lógica del negocio: cálculo de tarifas dinámicas de envío, validación de idempotencia, descuento atómico de inventario e inyección contextual de catálogo hacia el LLM.
Capa 5: Acceso a Datos (Spring Data Repositories & MongoTemplate)
Intermediario con MongoDB. Provee métodos CRUD automáticos y pipelines de agregación analítica para el cálculo de ventas y métricas financieras.
Capa 6: Persistencia NoSQL (MongoDB Database)
Base de datos documental `merkostore_db` organizada en 6 colecciones con índices y claves foráneas virtuales.

2.2. Flujo de Comunicación de una Transacción de Compra

  1. El cliente navega el catálogo público (`GET /api/v1/public/products`) y agrega artículos al carrito.
  2. Al pulsar "Completar Pedido", el frontend envía una solicitud POST /api/v1/orders con el DTO OrderRequest y una clave de idempotencia única.
  3. OrderController valida los campos y transfiere el payload a OrderService.
  4. OrderService descuenta las unidades de stock de cada producto en MongoDB, calcula la tarifa de domicilio según las políticas del negocio y persiste la orden con estado RECEIVED.
  5. El sistema genera el mensaje pre-estructurado y abre la pasarela de WhatsApp con el enlace de confirmación directo con el tendero.

4. Interfaz de Usuario y Experiencia de Uso

La interfaz de usuario fue diseñada con un enfoque minimalista y centrado en el tendero barrial y el cliente local, eliminando elementos distractores:

4.1. Vista Tienda Cliente (Storefront)

  • Banner Promocional y Búsqueda: Barra de búsqueda predictiva en tiempo real que filtra productos instantáneamente sin recargar la página.
  • Tarjetas de Producto Limpias: Presentan la imagen nítida del artículo, unidad de venta (kg, litro, bandeja), precio en COP y control numérico de cantidad integrado (+/-). Se eliminaron insignias invasivas y botones de favoritos superfluos.
  • Carrito Flotante & Checkout Drawer: Barra indicadora de cumplimiento de pedido mínimo y selector de método de despacho (Domicilio vs. Recogida en Tienda).
  • Pasarela WhatsApp: Generación automática de enlace transaccional para formalizar el pedido directamente con el tendero.

4.2. Vista Panel Administrativo (Backoffice)

  • Dashboard de Control Operativo: Tarjetas con total de ventas, pedidos en preparación y alertas de productos con bajo inventario.
  • Gestión de Inventario: Control de disponibilidad mediante interruptores de stock y botón de inactivación lógica que preserva la integridad de la base de datos.
  • Módulo de Visualización Power BI: Pestaña integrada que despliega el informe analítico ejecutivo para toma de decisiones gerenciales.
  • Módulo de Optimización Lineal (Investigación de Operaciones): Solucionador Simplex interactivo para determinar la producción óptima de combos con sincronización al catálogo de un solo clic.

4.3. Explicación de la Interacción entre Interfaz y Servicios Backend

La comunicación entre el cliente web (SPA) y el servidor Spring Boot se realiza mediante llamadas asíncronas REST a través de la Fetch API nativa de JavaScript encapsulada en el objeto modular API en app.js:

  • Inyección Automática de Credenciales: Cuando el tendero inicia sesión en el panel administrativo, el JWT emitido por /api/v1/auth/login se persiste en localStorage y se inyecta dinámicamente en la cabecera Authorization: Bearer <token> de cada petición hacia los endpoints de /api/v1/admin/**.
  • Consumo Reactivo y Asíncrono del Catálogo: Al cargar la vista de la tienda, se invoca GET /api/v1/public/products. La respuesta JSON se almacena en el estado global reactivo state.products y se renderiza en el DOM mediante plantillas de componentes.
  • Persistencia Desacoplada y Modo Offline-First: Ante una eventual caída o desconexión del servidor, el subsistema local Storage almacena en caché las operaciones, permitiendo continuar navegando y procesando órdenes de WhatsApp sin pérdida de disponibilidad.

5. Integración con Modelos de Lenguaje (LLM) — MerkoBot IA

5.1. Proveedor y Modelo de Lenguaje

  • Proveedor Cloud: Groq Cloud Platform.
  • Modelo Utilizado: llama-3.1-8b-instant (Meta AI Llama 3.1 con 8 mil millones de parámetros).
  • Mecanismo de Conexión: Consumo de la API REST /v1/chat/completions mediante llamadas HTTP asíncronas con token de autenticación protegido mediante variables de entorno (${GROQ_API_KEY:}).

5.2. Arquitectura de Inferencia RAG (Retrieval-Augmented Generation)

Para erradicar cualquier alucinación en precios o disponibilidad de artículos inexistentes, el servicio ChatbotService implementa un patrón **RAG en memoria**:

Mecanismo de Consulta Inteligente:
1. El usuario envía una pregunta como: "Tengo $30.000, ¿qué ingredientes me recomiendas para hacer un almuerzo familiar?".
2. El backend consulta en MongoDB únicamente los productos con isAvailable = true y stock > 0.
3. Se ensambla un System Prompt dinámico que contiene el catálogo real actualizado en ese preciso segundo.
4. El modelo genera recomendaciones precisas ajustadas estrictamente al presupuesto y al catálogo disponible.
5. El frontend renderiza botones de acción rápida ("chips") que permiten al cliente añadir la recomendación al carrito con un solo clic.

6. Modelo de Datos y Persistencia NoSQL

La base de datos documental merkostore_db se compone de las siguientes colecciones maestras y transaccionales:

Colección Claves Primarias e Índices Campos Principales Regla de Integridad
products _id (ObjectId), sku (Unique, Indexed) name, price, discountPrice, stock, categoryId, type (DETAL/MERCADO), isAvailable No se borra en admin; solo se inactiva para mantener histórico de ventas.
categories _id (ObjectId), slug (Indexed) name, icon, slug, displayOrder, isActive Admite eliminación física cuando no tiene productos dependientes.
orders _id (ObjectId), orderNumber (Unique, Indexed) customer (nombre, teléfono, dirección), items (array anidado), subtotal, deliveryFee, total, orderStatus, paymentStatus Generación automática de consecutivo único (ej. `ORD-202611-0089`). Admite eliminación de historial a petición del administrador.
users _id (ObjectId), username (Unique, Indexed) username, password (BCrypt), name, email, role (`ROLE_ADMIN`), isActive Protección contra eliminación del último administrador activo del sistema.
store_configs _id (ObjectId), storeId (Unique) storeName, whatsappPhone, address, deliveryFee, minimumOrder, isStoreOpen Configuración singleton del comercio barrial para reglas de checkout.
financial_transactions _id (ObjectId), orderId (Indexed) type (INCOME/EXPENSE), amount, category, paymentMethod, date Libro diario contable para auditoría y visualización analítica en Power BI.
